# 任务稳定性修复与迁移

适用于本次账本保护、并发准入、启动失败恢复、项目隔离及执行器停止修复。运行环境需要 Node.js 22.19 或以上。

## 升级

升级前停止旧版控制进程，保留数据库、项目账本和工作区的完整备份。避免旧版和新版控制进程同时写同一个数据库。首次用新版打开数据库时自动在事务中迁移；失败会回滚。

- `loop_queue` 改为按 `(project_id, unique_code)` 唯一；旧表保留为 `loop_queue_legacy`。
- `flags` 的唯一约束增加 `project_id`；旧表保留为 `flags_legacy`。
- 能从关联 job 确定项目的旧队列保留状态和次数。归属有歧义的行保留在 `project_id='@legacy'` 下，状态为 `blocked`，原因是 `migration_ambiguous_project`。核对原表和历史 job 后，再在正确项目中重新排队。
- 旧的无 job flag 无法证明属于哪个项目，因此保留在未分配范围；不会显示到每个项目中。工作区中的 flag 仍按工作区读取。
- 工作区目录和已有 goal 身份保持兼容。回滚旧程序时也应恢复升级前的数据库备份，不能直接让旧程序写入新表结构。

## 账本故障

读取账本不会创建、修复或覆盖文件。仅首次启动控制台会显式初始化默认项目。每次成功修改使用原子替换并保留上一版有效内容为 `data/console/ledger.json.bak`。跨进程写入通过 SQLite 锁及版本比较防止丢失更新；冲突返回 409，刷新后重试即可。

JSON 损坏、结构无效或已有数据时账本意外丢失，会返回 503 和 `ledger_unavailable`，界面保留上次成功加载的数据。恢复时先保存故障文件，检查 `.bak` 或离线备份确实包含需要的项目和任务，再停止控制进程并恢复账本。程序不会自动选取可能过期的备份覆盖原文件。

账本里找不到某项目不构成删除授权。后台清理只接受数据库中的明确删除标记。删除仍在运行的项目时，保留执行器身份、占用名额和运行文件；确认执行器退出后才清理这些内容。

## 执行与停止

所有实际执行入口在 SQLite `BEGIN IMMEDIATE` 事务中检查并发和资源占用，并创建 `starting` 记录，然后才进行工作区准备、平台启动和执行器启动。`starting`、`running`、`stopping` 都占名额；兼容旧版的 `queued` job 也保守计入。仅排队等待的 `loop_queue` 记录不占执行名额。

- 手动启动遇到满额会报告 `deferred_capacity`；批量任务保留待办并延迟重试。
- 停止请求按项目及任务定位，再按具体 job 停止 Local / Docker。启动中的取消会阻止后续启动；迟到的启动回调会立即请求停止。
- Docker 停止命令异常会尝试强制终止。Docker 失联或执行器身份不明时保留名额，并显示诊断信息，直到确认退出。不要仅为腾出名额而把这些 job 改成已完成。
- 新任务保存控制进程身份、启动期限和预期运行标识。控制进程退出后的未启动任务可收敛为 `startup_lost`。超出启动期限的操作不会继续启动执行器；控制进程仍活跃但启动操作未返回时保留占用并显示诊断。
- 停止标记单独按项目与任务持久化，即使停止发生在 goal 创建之前，重启也不会自动重跑；明确手动启动才清除标记。
- 启动准备异常不计作求解尝试；循环任务的准备异常会回到所属项目的队列，保留重试预算并延迟重试。

API 写操作应携带 `project_id`。停止接口省略项目时只兼容能唯一确定归属的任务；存在同名跨项目任务会拒绝操作。显式 `null` 表示未分配项目，不代表所有项目。

## 验证

```sh
npm test
npm run build
npx tsc -p console/tsconfig.json --noEmit
npm run test:release
```

另有显式启用的真实 Docker 停止测试：

```sh
HEIMDALL_DOCKER_TEST=1 npx vitest run test/docker-stop.test.ts
```

Docker 测试需要本地 `node:22.22.0-bookworm` 和 `alpine:3.20` 镜像。测试使用临时工作区、空闲脚本和独立容器，不调用模型或测试真实目标；结束后清理测试容器及临时镜像。
